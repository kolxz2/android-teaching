# Практика 04. Kotlin-логика состояния в FinanceApp

**Длительность:** 90 минут  
**Среда:** Android Studio, Git, эмулятор или устройство  
**Основа:** готовый стартовый экран FinanceApp на Jetpack Compose  
**Учебный репозиторий:** [FinanceApp](https://github.com/kolxz2/FinanceApp)

## Результат занятия

К концу практики студент:

- сохраняет свою работу перед обновлением и отличает `origin` от `upstream`;
- переносит обновления преподавателя в собственный репозиторий;
- моделирует доход и расход обычными Kotlin-типами;
- хранит данные экрана в неизменяемом состоянии;
- описывает действия пользователя через sealed-события;
- пишет чистую функцию `reduce(state, event)`;
- проверяет положительность суммы через `require`;
- связывает две кнопки с Kotlin-логикой;
- использует `internal` для внутренних сущностей приложения.

## Границы практики

Основная задача — Kotlin-логика. Compose-вёрстка меняется минимально: на экране остаются один `Text` и две `Button`.

На этой практике не добавляются поле ввода, навигация, ViewModel, база данных, новые экраны и сложная архитектура.

## Перед занятием преподавателю

1. Проверить, что Compose-миграция опубликована в `upstream/master` и отмечена тегом `v1.0.4`.
2. Не переписывать историю `upstream/master` после начала пары.
3. Проверить обновление старой студенческой версии командами из раздела «Обновление проекта из remote».
4. Иметь готовый diff миграции: `build.gradle.kts`, `app/build.gradle.kts`, `gradle/libs.versions.toml`, `MainActivity.kt`, удаление `activity_main.xml`.
5. До занятия выполнить `./gradlew detekt testDebugUnitTest lintDebug assembleDebug` на стартовой ветке.

> Compose-миграция опубликована в `upstream/master` и отмечена тегом `v1.0.4`. Студенческий `master` содержит собственный commit, поэтому обновление выполняется обычным merge, а не `--ff-only`.

## Обязательный порядок работы

Практика начинается только после обновления проекта:

1. проверить, что студент находится в чистой ветке `master`;
2. получить Compose-базу из удалённого учебного репозитория;
3. обновить свой `origin/master`;
4. выполнить Gradle Sync, сборку и запуск;
5. создать ветку `lecture-04`;
6. приступить к заданиям лекции 4.

У студентов нет незавершённой работы, поэтому предварительный commit и резервная ветка не нужны.

## Сценарий на 90 минут

- 0–15 минут — получение Compose-базы, Gradle Sync и запуск;
- 15–35 минут — изменение готовой вёрстки и добавление строковых ресурсов;
- 35–45 минут — перенос экрана в отдельный файл и проверка запуска;
- 45–55 минут — самостоятельное моделирование транзакции, состояния, события и reducer;
- 55–60 минут — перерыв;
- 60–75 минут — подключение состояния и двух кнопок к reducer;
- 75–82 минуты — проверка логики и модификатор `internal`;
- 82–90 минут — Detekt, сборка, commit и push.

## Обновление проекта из remote

Проверить состояние проекта:

```powershell
git status
git branch --show-current
```

Ожидается чистая ветка `master`. Затем добавить учебный remote и получить обновление:

```powershell
git remote -v
git remote add upstream https://github.com/kolxz2/FinanceApp.git
git fetch upstream
git switch master
git merge upstream/master -m "Update project to Compose"
git push origin master
.\gradlew.bat assembleDebug
git switch -c lecture-04
```

Если `upstream` уже существует, `git remote add` пропускается. Ветка `lecture-04` создаётся только после успешной сборки и запуска Compose-экрана. После выполнения заданий:

```powershell
git push -u origin lecture-04
```

Если merge сообщает о конфликте, студент не исправляет историю самостоятельно, а обращается к преподавателю.

## Сначала настраиваем вёрстку

Студенты получают экран с одним `Text`, одной кнопкой и состоянием `checkSucceeded`. До написания бизнес-логики нужно:

1. удалить `checkSucceeded` и условный выбор старых строк;
2. временно задать баланс `25_000` и счётчик `0` обычными локальными значениями;
3. в одном `Text` показать баланс и количество операций;
4. переименовать существующую кнопку в кнопку дохода;
5. добавить вторую кнопку расхода;
6. временно оставить оба `onClick = { }` пустыми;
7. запустить приложение и проверить внешний вид.

В `strings.xml` создать именно эти ресурсы:

```xml
<string name="balance_summary">Баланс: %1$d ₽\nОпераций: %2$d</string>
<string name="add_income_button">Добавить доход 500 ₽</string>
<string name="add_expense_button">Добавить расход 250 ₽</string>
```

После успешного запуска перенести `FinanceAppScreen` и Preview в отдельный `FinanceAppScreen.kt`. Готовые `Surface`, `Column`, отступы и выравнивание не менять.

## Затем добавляем поведение

- начальный баланс — `25 000 ₽`;
- кнопка дохода добавляет `500 ₽`;
- кнопка расхода вычитает `250 ₽`;
- каждая операция увеличивает счётчик операций на один;
- операция представлена отдельной моделью с суммой и типом;
- сумма операции должна быть положительной;
- reducer не изменяет старое состояние, а возвращает новое.

Реализацию контракта состояния студенты проектируют самостоятельно по этим требованиям. Вместо готового решения они получают наводящие вопросы:

- какие два числа нужны экрану постоянно;
- какой тип лучше описывает два варианта операции;
- какие данные обязательны для одной транзакции;
- какое единственное событие достаточно для обеих кнопок;
- где проверить положительность суммы;
- как получить новое состояние, не меняя старое.

## Подсказки по остальным файлам

### MainActivity.kt

- оставить `MainActivity` точкой входа Android;
- внутри `setContent` вызвать тему и `FinanceAppScreen`;
- тему можно оставить в этом же файле;
- `MainActivity` остаётся публичной, а тема получает `internal`.

### FinanceAppScreen.kt

- сохранить существующие `Surface` и `Column` без перестройки расположения;
- сначала собрать экран на временных значениях и с пустыми `onClick`;
- после реализации Kotlin-логики заменить временные значения на состояние через `remember` и `mutableStateOf`;
- первая кнопка создаёт доход и отправляет событие в reducer;
- вторая кнопка создаёт расход и отправляет событие в reducer;
- результат reducer присваивается переменной состояния;
- функция экрана получает `internal`.

### strings.xml

Использовать три ресурса, перечисленные в разделе «Сначала настраиваем вёрстку».

## Самопроверка логики

1. Доход `500 ₽` из начального состояния даёт баланс `25 500 ₽` и одну операцию.
2. Следующий расход `250 ₽` даёт баланс `25 250 ₽` и две операции.
3. Исходное состояние после reducer не изменяется.
4. Нулевая или отрицательная сумма отклоняется проверкой контракта.

## Критерии готовности

- проект синхронизируется, собирается и запускается;
- на экране один информационный текст и две кнопки;
- доход увеличивает баланс, а расход уменьшает;
- счётчик операций изменяется после каждой кнопки;
- вычисления выполняет reducer, а не composable-разметка;
- пользовательские строки находятся в `strings.xml`;
- внутренние модели, события, reducer, экран и тема объявлены как `internal`;
- `MainActivity` остаётся публичной точкой входа;
- работа сохранена в ветке `lecture-04` и отправлена в собственный `origin`.
