# Заметки лектора к лекции 07: ViewModel в FinanceApp

Этот материал объясняет именно реализацию ветки `FinanceApp/lecture-07`, созданной от `lecture-04`. Начните с запуска приложения, затем открывайте исходники в порядке `MainActivity.kt` → `TransactionScreen.kt` → `MainUiState.kt` → `TransactionViewModel.kt` → `legacy/`. На экране можно ввести описание и положительную целую сумму, выбрать доход или расход и добавить операцию.

## 1. Зачем здесь ViewModel

В лекции 4 `FinanceAppScreen` хранил `MainUiState` через `remember { mutableStateOf(...) }` и сам вызывал `reduce` после нажатия кнопки с заранее заданной суммой. Экран отвечал одновременно за отображение и за изменение состояния. В лекции 7 форма стала интерактивной: черновик, проверка ввода, баланс и история должны иметь одного владельца. Им стала `TransactionViewModel`.

`ViewModel` из AndroidX — держатель данных и логики **конкретного UI-экрана**. Она не рисует элементы и не хранит ссылки на Activity, View или composable. `viewModel()` из `lifecycle-viewmodel-compose` получает экземпляр у `ViewModelStoreOwner`; при повторной композиции возвращается тот же экземпляр. При обычном пересоздании Activity, например после поворота, ViewModel сохраняет состояние. После завершения процесса приложения или окончательного закрытия экрана её память не гарантируется. Для восстановления черновика после смерти процесса понадобятся `SavedStateHandle` или `rememberSaveable`, а для постоянной истории — репозиторий и хранилище. Нынешняя история существует только в памяти ViewModel.

Не смешивайте жизненный цикл ViewModel с жизненным циклом composable: composable может выполняться снова при рекомпозиции, а объект ViewModel от этого не создаётся заново. ViewModel очищается, когда её владелец удаляется окончательно. В этом приложении вызов идёт из `MainActivity`, без Navigation Compose; владельцем является Activity.

## 2. Какие технологии использованы

| Часть | Роль в примере |
| --- | --- |
| Kotlin `data class`, `enum class`, `sealed interface` | Модель состояния, два типа транзакций и закрытый набор событий. |
| AndroidX `ViewModel` | Владелец состояния и обработчика событий экрана. |
| `lifecycle-viewmodel-compose` и `viewModel()` | Получение ViewModel из composable с привязкой к владельцу жизненного цикла. |
| Compose `mutableStateOf` | Наблюдаемое состояние: присваивание нового `uiState` запускает нужную рекомпозицию. |
| Jetpack Compose и Material 3 | `OutlinedTextField`, `FilterChip`, `Button`, `Text`, `Surface` строят форму из состояния. |
| Android `strings.xml` и `stringResource` | Подписи, ошибки и форматированные строки интерфейса. |
| JUnit | Проверка сценариев событий, дохода и расхода. |

## 3. Контракт состояния

`MainUiState` — снимок того, что нужно экрану сейчас. `amount` и `description` — **строки черновика**, потому что ввод текста может быть пустым и ещё не являться числом. `type` — выбранный `TransactionType`. `balance`, `transactionCount` и `transactions` описывают уже добавленные операции. `error: TransactionError?` задаёт вид ошибки без готового текста; UI сопоставляет enum с ресурсом.

`Transaction` — уже подтверждённая операция: целочисленная сумма, тип и описание. Черновик нельзя автоматически считать транзакцией. Только после проверки `addTransaction()` создаёт `Transaction` и отправляет `MainUiEvent.AddTransaction`.

Текущий баланс начинается с нуля. Доход прибавляет сумму, расход вычитает. Поэтому расход 250 ₽ без предварительного дохода даёт −250 ₽: это сознательное поведение учебного примера, а не запрет отрицательного баланса. `transactionCount` увеличивается вместе с историей. После успешного добавления поля ввода очищаются, выбранный тип остаётся прежним.

## 4. События и однонаправленный поток данных

На экране нет прямого присваивания `uiState`. Пользователь меняет поле — `onValueChange` отправляет `AmountChanged` или `DescriptionChanged`. Нажатие `FilterChip` отправляет `TypeChanged`. Кнопка вызывает `addTransaction()`: ViewModel проверяет черновик и отправляет `InvalidTransaction`, `AmountTooLarge` либо `AddTransaction`.

```text
Действие пользователя
    → MainUiEvent / addTransaction()
    → TransactionViewModel.onEvent()
    → reduce(старое состояние, событие)
    → новое значение uiState
    → Compose читает uiState и обновляет экран
```

Это однонаправленный поток: данные идут из ViewModel в UI, действия идут из UI в ViewModel. `reduce` в текущей реализации — приватная функция ViewModel, которая по старому состоянию и событию возвращает новое. `state.copy(...)` не изменяет прежний объект, а создаёт новый снимок. Присваивание `uiState = reduce(uiState, event)` делает изменение видимым Compose через `mutableStateOf`.

Разберите на доске `AmountChanged("250")`: reducer принимает только цифры, меняет черновик `amount` и сбрасывает прежнюю ошибку; баланс не меняется. Затем `TypeChanged(INCOME)` меняет выбор. После `AddTransaction(Transaction(250, INCOME, "Зарплата"))` баланс увеличивается, операция добавляется в историю, счётчик растёт, поля очищаются. UI перечитывает новое состояние.

## 5. Валидация и ошибки

`addTransaction()` преобразует текст суммы через `toIntOrNull()`, удаляет пробелы вокруг описания и проверяет положительную сумму и непустое описание. Пустое или нулевое значение и пустое описание отправляют `InvalidTransaction`. Значение за пределами `Int` отправляет отдельное событие `AmountTooLarge`, поэтому экран показывает ошибку о слишком большой сумме. Для переполнения итогового баланса `reduce` считает в `Long`, проверяет диапазон `Int` и оставляет баланс без изменения с ошибкой `AMOUNT_TOO_LARGE`.

`TransactionError` хранит смысл ошибки, а не русский текст. `TransactionScreen` выбирает `R.string.transaction_invalid_input` или `R.string.transaction_amount_too_large` и вызывает `stringResource`. Такой код позволяет переводить интерфейс без передачи `Context` внутрь ViewModel. Утверждения `require(...)` в ветке `AddTransaction` защищают инвариант при вызове события напрямую; обычный путь через кнопку выполняет проверку раньше.

## 6. UI и ресурсы

`TransactionScreen(viewModel: TransactionViewModel = viewModel())` читает `viewModel.uiState`. Каждое поле получает `value` из состояния и callback, создающий событие. Это контролируемые поля: источником правды остаётся ViewModel. `FilterChip.selected` сравнивает тип из состояния. Кнопка вызывает метод ViewModel. История строится из `transactions` в обратном порядке, поэтому новые записи видны сверху.

Видимые подписи и сообщения хранятся в `app/src/main/res/values/strings.xml`. Для баланса и строк истории используются форматные аргументы (`%1$d`, `%1$s`, `%2$d`). `stringResource` вызывается в composable; ViewModel не зависит от ресурсов Android. Для большого списка операций нынешний `Column` с `verticalScroll` стоит заменить на `LazyColumn`, но это отдельная тема о списках.

## 7. Пределы учебного решения

- ViewModel не сохраняет историю на диск и не выполняет сетевых запросов. После смерти процесса данные могут исчезнуть.
- `mutableStateOf` здесь достаточно для одного экрана Compose. В более сложном приложении часто используют `StateFlow`, репозиторий и `collectAsStateWithLifecycle`, но в этой ветке они не применены.
- Баланс хранится как `Int` в рублях без дробной части. Для реальных финансовых сумм обычно выбирают минимальные денежные единицы и отдельную модель валюты.
- В истории нет постоянного ID; при развитии списка он понадобится для стабильных ключей.
- Старые `legacy/FinanceAppScreen.kt` и `legacy/MainUiState.kt` сохранены как исходная точка сравнения. Они не вызываются из активного `MainActivity`.

## 8. Ход занятия на 90 минут

1. **0–10 мин:** показать готовый экран и сравнить с кнопками лекции 4.
2. **10–25 мин:** подробно объяснить ViewModel, владельца, пересоздание Activity и пределы хранения.
3. **25–40 мин:** разобрать `MainUiState`, `Transaction`, `TransactionError`, `MainUiEvent`.
4. **40–60 мин:** проследить поток одного действия через `onEvent` и `reduce`; выполнить доход, расход и ошибку.
5. **60–75 мин:** показать связь `mutableStateOf` с рекомпозицией, управляемые поля и `stringResource`.
6. **75–90 мин:** студенты добавляют новое событие, проговаривают путь данных и проверяют результат.

## Контрольные вопросы

**Что делает ViewModel?** Владеет состоянием экрана и обрабатывает действия; интерфейс читает готовое состояние.

**Почему нельзя хранить ViewModel через `remember`?** `remember` привязан к месту композиции; `viewModel()` получает экземпляр у `ViewModelStoreOwner` и обеспечивает нужный жизненный цикл.

**Что переживает поворот?** Состояние текущей ViewModel при обычном пересоздании Activity. Смерть процесса требует другого механизма восстановления.

**Почему сумма в форме — String?** Пользователь может временно оставить поле пустым; преобразование и проверка нужны при добавлении операции.

**Почему UI не меняет баланс напрямую?** Баланс меняется только после события добавления и проверки, поэтому все изменения проходят по одному пути.

**Почему ошибка — enum, а не строка?** Смысл ошибки остаётся в состоянии; локализованный текст выбирает UI из ресурсов.
